## 二、分层架构概览

MiniCode 是一个基于 Rust 构建的终端 AI Coding Agent，采用 Cargo Workspace 多 crate 分层架构，共 20 个 crate 按职责划分为六层：

| 层级 | 核心职责 |
|------|---------|
| TUI 交互层 | 基于终端的全屏 UI，负责按键输入、渲染对话内容、处理审批弹窗、展示流式输出 |
| Agent 核心层 | 驱动 model→tool→model 任务循环，管理多步工具链调用，协调上下文压缩，处理流式响应与错误恢复 |
| 能力编排层 | 统一管理内置工具与 MCP 外部工具，发现/加载 Skill，提供统一的工具调用接口 |
| 安全管控层 | 三级权限检查（路径/命令/编辑），危险命令规则识别，审批流程编排，操作前 Diff 预览 |
| 记忆持久层 | 会话消息 TOML 持久化，输入历史管理，MINI.md/CLAUDE.md 指令发现与会话元数据索引 |
| 基础设施层 | LLM API 适配（Anthropic Messages 格式），SSE 流式解析，JSON Schema 校验，全局运行时配置 |

## 三、从输入到输出的完整流程

用户从敲下回车键到看到 Agent 完成回复，整个过程经历以下 7 个阶段：

TEXT User Interface 文本用户界面
### 阶段 1：启动初始化

```
CLI 参数解析 → 会话ID确定 → 运行时存储初始化 → 工具注册表创建
    → MCP Server 并行启动 → 模型适配器选择 → TUI 进入事件循环，用户可以开始提问了
```
CLI 参数解析就是把用户在终端输入的命令行参数（ minicode --resume abc123 --model claude 这样的）转换成程序内部的配置。

运行时存储初始化就是 准备好程序运行时需要用到的数据存储结构 。程序运行过程中会产生很多数据（对话历史、会话元数据、用户配置等），这些数据需要存在磁盘上，重启后还能找回来

- 支持三种启动模式：新会话、恢复历史会话（`--resume`）、指定 session_id 恢复
- 工具注册表在启动时一次性创建，内置工具立即注册；MCP Server 并行连接（45s 启动超时，3s 列表超时），连接成功后动态注册其工具/资源/Prompt
- 模型适配器默认使用 Anthropic API，支持 Mock 模式用于测试

### 阶段 2：输入收集与预处理

```
用户输入 → 输入校验（非空判断）→ Slash命令分流 → 工具快捷方式分流 → 普通对话
```
判断三选一
- **Slash 命令**（`/` 开头）：本地命令直接处理（如 `/exit`、`/compact`、`/help`、`/skills` 等），不经过模型
- **工具快捷方式**（如 `!ls`）：直接执行单个工具，绕过模型推理，快速操作
- **普通对话**：追加用户消息到消息列表，写入输入历史，进入 Agent 回合

### 阶段 3：系统提示词构建

```
基础提示词模板 → 多目录指令发现（全局/项目/祖先目录/rules）
    → 可用Skill列表注入 → 工具Schema注入 → 拼装完整System Prompt
```

## MINI.md / CLAUDE.md 是什么？

### 和 Tool 的关系
- Tool（工具） 是原子能力——读文件、写文件、执行命令，模型直接调用就产生副作用
- Skill（技能） 是工作流指引——一份Markdown文档，告诉模型"遇到XX类型任务时，推荐按照以下步骤做：先...再...最后..."，本身不执行任何操作，只是 指导模型更好地使用 Tool
类比：Tool 是工具箱里的锤子、螺丝刀，Skill 是操作手册——"组装家具时，步骤1用螺丝刀拧紧，步骤2用锤子敲入"。模型读了操作手册，才知道什么情况下用什么工具、按什么顺序用。

### 阶段 4：Agent 任务循环（核心）

这是整个系统最核心的执行引擎，采用 `model → tool → model` 的循环模式：

每一步循环的详细过程：

**4.1 发送请求**
- 将完整消息列表（System + 历史对话 + 当前上下文）发送给 LLM API
- 启用 SSE 流式传输，模型输出逐 token 到达
- 流式文本增量实时推送到 TUI 渲染，用户看到打字机效果

**4.2 解析响应**
- 流式事件分三类：`content_block_delta`（文本增量/thinking增量）、`content_block_start/stop`（块边界）、`message_delta`（stop_reason等）
- 累积 thinking 块和 text 块内容
- 当收到 `stop_reason = "tool_use"` 时，解析工具调用（名称+JSON参数）
- 当收到 `stop_reason = "end_turn"` 时，将累积的文本作为最终回复，回合结束

message_delta 是 SSE 流中 消息级别 的增量事件，
和 content_block_delta （内容块级别）相对
- content_block_delta ： 正文在一点点到 ——文本、思考过程、工具参数的逐字输出
- message_delta ： 正文发完了，给个收尾信息 ——最重要的就是 stop_reason （告诉 Agent 是任务结束还是要调工具），以及用了多少 token

一次模型回复可能包含：
1. 一个 thinking 块："让我先看看 src 目录有什么文件"
2. 一个 tool_use 块： list_files({"path": "src"})
3. （工具执行后）一个 thinking 块："找到了 main.rs，让我读一下"
4. 一个 tool_use 块： read_file({"path": "src/main.rs"})
5. （工具执行后）一个 text 块："我看了代码，问题在第42行..."
## content_block_start/stop 的作用
它们是用来标记" 一个内容块的开始和结束 "的。想象成每段内容前后都有标签


**4.3 错误恢复（贯穿整个请求过程）**
- **429/5xx 错误**：指数退避 + 随机抖动重试，解析 Retry-After 头
- 429 = 请求太频繁，被限流了（Too Many Requests）
- 5xx = 服务端内部错误（500、502、503、529等），服务器那边出问题了

- **空响应**（模型提前停止无输出）：自动减小 max_tokens 续传
  空响应的情况 ：
- API 返回 200（成功），但 content 是空的，stop_reason 可能是 max_tokens
- 意思是模型"想说的话超过了 max_tokens 限制，但一个字都没吐出来就被截断了"

- **Thinking 中断**（thinking块未闭合）：截断到最后一个换行，设置 `pause_turn: true` 自动续传
- **token 超限**：触发紧急自动压缩后重试

**4.4 上下文压缩检查（三级渐进策略）**

在每次工具调用前，检查当前上下文 token 数：

| 级别 | 触发阈值 | 是否调用模型 | 策略 |
|------|---------|-------------|------|
| Microcompact | 上下文使用 ≥ 50% | 否 | 清理历史中旧的只读工具结果（read_file/list_files/grep_files等），保留最近3条完整结果，替换为 `[Content cleared]` 占位符 |
| Snip Compact | 上下文使用 ≥ 70% | 否 | 基于消息组（tool_use+tool_result配对）的安全剪枝——识别不含文件编辑、错误消息、未闭合调用的连续"安全区间"，批量删除并插入 SnipBoundary 标记 |
删除对模型后续推理不会造成影响的内容  比如说连续的只读工具调用（read_file/list_files/grep_files等）
删除的是整个消息组  而 microcompact 是删除 工具消息结果哦 保留消息结构

| Auto Compact | 上下文 ≥ 128k tokens | 是 | 保留最近12条消息，将更早的历史发送给模型生成结构化 ContextSummary（包含关键决策、操作文件、错误信息、下一步计划），替换历史消息 |

压缩具有降级链：模型摘要失败 → 使用基于 turn 序号的规则摘要 → 均失败则硬截断，确保永不卡住。

**4.5 权限安全审批**

工具执行前必须通过三级权限检查：

- **路径权限**：检查文件/目录路径是否在允许范围内（cwd 下），支持 glob 模式
- **命令权限**：通过规则引擎分类危险等级
  - 低风险：git status、git log、ls、cat 等 → 直接执行
  - 高风险：git reset --hard、git clean -f、git push --force、npm publish、pip install、解释器直接执行等 → 弹窗审批
- **编辑权限**：write_file/edit_file/patch_file → 展示 unified diff 预览后审批

审批弹窗支持 6 种决策粒度：
1. 仅本次允许
2. 本回合允许该操作
3. 本回合允许所有此类操作
4. 永久允许（写入权限配置文件）
5. 拒绝本次并给模型反馈
6. 永久拒绝

审批通过 oneshot channel 从后台任务发送到 UI 主线程，用户按键后将决策回传，工具继续或中断执行。

**4.6 工具执行**

- 内置工具（12个）：list_files、grep_files、read_file、write_file、edit_file、patch_file、run_command、ask_user、load_skill、web_fetch、web_search、kill_process
- MCP 工具：命名格式为 `mcp__server_name__tool_name`，调用时自动路由到对应 MCP Server
- 每个工具执行前通过 JSON Schema（Draft 7）校验参数合法性
- 工具结果截断保护：超大输出自动截断并提示使用 grep 缩小范围
- run_command 支持后台任务（命令末尾加 `&`），执行后立即返回 job_id，不阻塞 Agent 循环

**4.7 结果回传 & 继续循环**

- 工具结果封装为 tool_result 消息追加到消息列表
- 消息持久化到磁盘（每条消息追加后立即写入 TOML）
- 回到 4.1，继续发送请求给模型，开始下一轮 tool_use 循环
- 若模型本轮未调用工具（返回纯文本），回合结束

### 阶段 5：流式渲染更新

TUI 主线程与 Agent 后台任务通过 unbounded channel 通信：

```
Agent后台任务                    TUI主线程
    │                              │
    │── TurnEvent::StreamDelta ──→ │ 累积流式文本，实时渲染
    │── TurnEvent::ToolStart ────→ │ 更新状态栏 "Running xxx..."
    │── TurnEvent::ToolResult ──→ │ 折叠/展开工具结果，更新Token估算
    │── TurnEvent::Approval ────→ │ 弹出审批弹窗，等待用户按键
    │── TurnEvent::AskUser ─────→ │ 弹出选择题弹窗
    │── TurnEvent::Progress ────→ │ 显示系统通知（如压缩通知）
    │── TurnEvent::Done ────────→ │ 回合结束，回到Ready状态
    │                              │
```
## mpsc 全称
mpsc = Multiple Producer, Single Consumer（多生产者，单消费者）
这是一种经典的并发设计模式，意思是： 多个发送方可以往同一个通道里发消息，但只有一个接收方来处理这些消息 。

- 多生产者 ：Agent 循环中可能有多个地方需要发消息（流式响应、工具执行、审批请求），都通过同一个发送端（通道）发送
- 单消费者 ：UI 渲染必须在主线程进行，不能多个线程同时操作终端（会乱），所以只有一个接收端
- 无界 ：流式响应可能产生很多 delta 消息，如果队列有限制会阻塞发送，影响用户体验

- UI 以 16ms 间隔轮询事件通道和终端输入，保证 60fps 响应
- 流式文本最终落地后冻结增量，忽略迟到 chunk 防止乱序
- Agent 执行期间用户仍可输入，输入排队到 queued_busy_inputs，回合结束后自动注入发起新回合

### 阶段 6：会话持久化

每条消息追加时：
- 追加到内存中的消息列表（Vec<ChatMessage>，Mutex 保护）
- 立即序列化追加写入 TOML 文件（追加写入，非全量覆盖）
- 输入历史单独持久化，支持上下键浏览历史输入

退出时：
- 写入会话元数据（session_id、创建/结束时间、cwd、回合数、用户输入数、状态）
- 维护会话索引文件，供 `--resume` 时列出和选择历史会话

### 阶段 7：会话恢复

```
用户选择恢复 → 读取会话元数据 → 加载TOML消息文件
    → 重建消息列表 → 估算当前Token → 进入TUI主循环
    → 用户可在此基础上继续对话
```

## 五、关键设计决策

### 5.1 异步架构：Tokio 多任务 + Channel 通信
- Agent 回合在 tokio::spawn 后台任务中执行，不阻塞 UI 主线程
- 后台任务与 UI 之间通过 mpsc::UnboundedChannel 单向传递事件
- 权限审批通过 oneshot channel 实现同步等待：后台任务发送审批请求→阻塞等待→UI处理后回传决策
- 支持用户在 Agent 忙时输入排队，回合结束自动消费排队输入发起新回合

### 5.2 三级压缩的设计哲学
- **不丢信息 vs 降 Token**的权衡：Microcompact 只清只读结果（可重新读取），SnipCompact 基于消息组安全剪枝（保证不破坏 tool_use/tool_result 配对），AutoCompact 调用模型摘要（保留语义信息）
- 渐进触发而非一次性激进压缩，让 Token 成本下降更平滑
- SnipBoundary 标记让模型知道历史有剪枝，避免幻觉

### 5.3 MCP 多协议自动协商
- 优先尝试 Content-Length framing（标准JSON-RPC），失败回退 Newline-JSON（每行一个JSON），最后尝试 Streamable HTTP
- 所有 Server 并行连接，使用 FuturesUnordered 并发收集结果
- 每个 Server 独立超时，单个 Server 启动失败不影响其他 Server 和整体启动
- Header 支持环境变量模板（如 `Authorization: Bearer $MCP_TOKEN`），启动时解析

### 5.4 安全模型：默认拒绝，按需授权
- 所有不在白名单内的危险操作必须审批
- 文件编辑前展示 Diff，支持"拒绝并反馈"让模型知道为什么被拒绝
- 权限记忆最小粒度：路径级允许、危险命令类允许
- 每个回合开始 begin_turn()，结束 end_turn()，回合级权限自动清理；永久权限写入磁盘

### 5.5 错误恢复的多层防御
- 网络层：指数退避重试 + Retry-After 解析
- 响应层：空响应自动续传、thinking截断自动修复
- 上下文层：Token 超限触发压缩后重试
- 压缩层：模型摘要失败→规则摘要→硬截断的降级链
- 任何一步失败都尽量不中断用户体验
