MiniCode (RushCode) AI应用开发                 2025.xx - 2026.xx

项目简介 ：参考 Claude Code 架构，使用 Rust 实现终端 AI Coding Agent，基于 Query Loop + Tool Use 构建 model→tool→model 任务执行闭环，重点设计 Skill 能力体系、自进化记忆沉淀、分层上下文压缩、多协议 MCP 工具集成与权限安全审查机制，提升复杂任务下的执行准确率、上下文稳定性与操作安全性。

技术栈 ：Rust、Tokio、MCP、Tool Calling、Memory System、Context Compaction、Skill System、Async/Await

技术亮点 ：

- Skill 能力体系 ：设计多作用域分层 Skill 机制，将原子 Tool、高层 Skill 工作流与多目录技能源分层组织，结合 YAML 元信息标签解析、系统提示词概览注入与 load_skill 按需加载进行二阶段获取，解决 Skill 规模增长下的上下文膨胀、噪声干扰与 Token 成本过高问题，支持 add/remove 命令实现能力模块化扩展。
- 自进化记忆沉淀 ：设计自进化记忆沉淀机制，将会话历史、指令规则与用户偏好分层提炼为可复用记忆资产，构建"执行-持久化-摘要压缩-跨会话复用"闭环：对话历史通过 TOML 持久化与 ContextSummary 实现断点恢复，MINI.md/CLAUDE.md 与 rules 目录自动发现沉淀程序性经验，权限审批决策持久化学习用户偏好，实现跨会话上下文延续与错误修复加速。
- 分层上下文压缩 ：设计三级渐进式上下文压缩机制，将只读工具结果占位清理、安全区间确定性剪枝与模型生成摘要兜底结合，构建"微压缩清理-安全剪枝-超限摘要"的上下文治理闭环——Microcompact 清理旧 tool_result 占位释放 Token，SnipCompact 基于消息组安全区间剪枝保护编辑与错误上下文，AutoCompact 调用模型生成结构化摘要保留关键决策，在保证长会话稳定性的同时降低 Token 成本。
- 多协议 MCP 工具生态 ：设计多协议 MCP 动态接入机制，将 Content-Length、Newline-JSON、Streamable HTTP 三种传输协议自动协商回退，结合 FuturesUnordered 并行连接启动、动态工具注册与 Header 环境变量鉴权透传，实现远端工具/资源/Prompt 的热插拔扩展，MCP 工具自动注册为 mcp__server__tool 格式，无需修改核心即可接入搜索、文件系统等外部能力。
- 权限与安全审查 ：构建规则引擎过滤、Schema 参数自检与人工审批确认的多层审查链路，危险命令规则引擎识别 Git 破坏性操作、npm publish 与解释器执行等风险，JSON Schema 校验工具输入合法性，文件编辑前展示 unified diff 并支持拒绝反馈，结合单次/回合/永久等多粒度权限决策持久化，提升 Agent 在真实开发环境下的可控性与安全性。

这个项目采用单 Agent 架构，核心考量是 专注于工具链的深度整合和用户体验优化 。单 Agent 模式在个人开发场景下已经足够强大——通过丰富的内置工具（文件操作、命令执行、网络搜索）、MCP 外部工具扩展、以及 Skill 工作流指引，模型能够完成从代码分析到修改到验证的完整开发链路。多 Agent 架构更适合大型团队协作或超复杂任务分解，对于个人开发者来说，单 Agent 的响应速度和简单性更有优势。未来可以考虑在单 Agent 基础上扩展任务分解能力，让模型能够将复杂任务拆分为多个子任务顺序执行。

## Skill 能力体系 — 面试要点总结

### 1. 多作用域分层 Skill 机制

**"多作用域分层"有两层含义：**

**第一层：按目录分层（作用范围）**
- 全局级：`~/.minicode/skills/`，所有项目通用，适合放通用技能
- 项目级：`<project>/.minicode/skills/`，只在本项目生效，适合放项目特定工作流
- 兼容级：`.claude/skills/`，兼容 Claude Code 的技能目录

**第二层：Skill 内部分层（内容结构）**
- 元信息层：YAML frontmatter（name + description），用于概览注入
- 正文层：完整工作流程内容，按需加载

---

### 2. 模块化扩展（add/remove 命令）

**"模块化"指的是：**
- 每个 SKILL.md 是一个独立的功能模块，像搭积木一样自由增删
- 加一个 SKILL.md 文件 = Agent 多一个能力
- 删一个 SKILL.md 文件 = Agent 少一个能力
- 不需要改任何代码，不需要重启服务
- 各技能之间互不影响，修改一个不影响其他

---

### 3. 上下文膨胀、噪声干扰与 Token 成本问题

**解决方案：二阶段获取机制**

| 阶段 | 时机 | 注入内容 | Token 消耗 |
|------|------|---------|-----------|
| 阶段一 | 启动时 / 回合开始 | 只注入 Skill 名称 + 一句话描述（概览） | 极少，可忽略 |
| 阶段二 | Agent 循环中，模型自主决定 | 调用 `load_skill` 工具加载对应 Skill 全文 | 只加载需要的那一个 |

**解决了什么问题：**
- **Token 成本**：不是把所有 Skill 正文全塞进上下文，而是用哪个加载哪个
- **噪声干扰**：上下文保持干净，模型不会被无关技能内容误导，减少了幻觉
- **自主决策**：模型根据任务类型自己判断需不需要加载某个 Skill，不是被动全量注入

Schema = 数据的结构说明书
告诉计算机："一段数据应该长什么样，有哪些字段，每个字段是什么类型。"

## 三种可复用记忆资产
### 1. 对话历史（TOML 持久化 + ContextSummary）
这是 最基础的记忆 ，存的是你和模型的完整对话内容。
解决：跨会话断点恢复，不用每次从头开始聊
- 存储方式 ： messages.toml （每条消息追加写入）
- 怎么复用 ：
  - 恢复会话时，把历史消息加载到内存，模型接着上次的话题聊
  - 上下文超限时，生成 ContextSummary（把早期对话压缩成摘要），保留关键信息
类比 ：就像你和朋友聊天，每次聊天结束后，把聊天记录存下来。下次见面，你们可以接着上次的话题聊，不用从头开始。

### 2. 指令规则（MINI.md/CLAUDE.md + rules 目录）
这是 程序性经验 ，告诉模型"这个项目有什么规则、应该怎么做"。
解决：沉淀项目规则和工作流程
- 存储方式 ：项目根目录或 .minicode/ 目录下的 MINI.md、CLAUDE.md、rules/*.md 文件
- 怎么复用 ：每次会话开始时，自动发现并加载这些文件，注入到系统提示词中
- 特点 ： 不是程序自动写的，是用户手动编写的 ——你作为开发者，把项目的编码规范、工作流程写进这些文件，模型每次启动都能读到
类比 ：就像你进公司第一天，HR 给你一本《员工手册》，告诉你公司的规章制度、办事流程。每次你来上班，都能看到这本手册。

### 3. 用户偏好（权限审批决策持久化）
这是 行为习惯学习 ，记录用户对权限审批的决策。
解决：记录用户的安全偏好，避免重复审批
- 存储方式 ： permissions.json （项目级或用户级）
- 怎么复用 ：
  - 用户第一次遇到危险命令时，需要手动审批（允许/拒绝）
  - 审批决策被记录下来，下次遇到同类操作时自动应用
  - 支持"仅本次""本回合""永久"三种粒度
类比 ：就像你的手机，第一次安装一个应用时，它会问你"是否允许访问相册"，你选择了"允许"。下次这个应用再访问相册，手机就不会再问你了，直接按你的偏好处理。

可复用记忆资产
├── 对话历史（TOML + ContextSummary）
│   → 解决：跨会话断点恢复，不用每次从头聊
│   → 存储：每次对话自动保存
│
├── 指令规则（MINI.md/CLAUDE.md + rules）
│   → 解决：沉淀项目规则和工作流程
│   → 存储：用户手动编写，每次会话自动加载
│
└── 用户偏好（权限决策持久化）
    → 解决：记住用户的安全偏好，减少重复审批
    → 存储：用户审批时自动记录，下次自动应用

ContextSummary 会被保存到 messages.toml ，但它不是作为一条 独立的新消息 追加进去，而是 替换掉被压缩的那些历史

安全区间 = 一段可以放心删除的连续消息组，不会破坏模型理解

### 先理解"消息组"
每次模型调用工具，都会产生一对消息： tool_use （模型调用工具）+ tool_result （工具返回结果），这就是一个消息组。
文件编辑，错误消息，未闭合调用（工具还在执行） 这些消息是不可以删除的
SnipCompact 会扫描消息列表，找出 连续的、不含上述不安全内容的消息组序列 。

MCP = Model Context Protocol（模型上下文协议）
它是 Anthropic 提出的一个 标准化协议 ，用来让 AI Agent 和外部工具服务进行通信。
### 核心思想
你可以把 MCP 理解成一个 工具市场 ：

- MCP Server ：提供工具的一方（比如一个搜索服务、一个浏览器服务、一个数据库服务）
- MCP Client ：使用工具的一方（就是这个项目，MiniCode）
- 协议 ：规定了双方怎么互相发现、怎么调用、怎么传递数据

### "设计多协议 MCP 动态接入机制"
MCP 协议本身规定了几种不同的数据传输方式（协议版本），不是所有 Server 都支持同一种方式。所以项目需要 动态检测并适配 不同 Server 的协议版本。

MCP 支持的三种通信方式：

协议 工作方式 特点 
Content-Length  标准的 HTTP 请求-响应，每次调用工具时，请求体里包含 JSON，响应体里返回结果 最简单，但每次调用都要等完整响应 
Newline-JSON 建立长连接，每次工具调用是一行 JSON，响应也是一行 JSON，用换行分隔 更高效，连接可以复用 
Streamable HTTP 支持流式传输，工具调用的结果可以分块返回（比如搜索结果一页一页传） 最灵活，适合大结果

自动协商回退 的意思是：
1. 先尝试最高级的 Streamable HTTP
2. 如果 Server 不支持，回退到 Newline-JSON
3. 如果还不行，最后用最基础的 Content-Length

### "结合 FuturesUnordered 并行连接启动"
FuturesUnordered 是 Rust Tokio 提供的一个工具，可以 同时启动多个异步任务 。

比如配置了 3 个 MCP Server：
- 搜索服务
- 浏览器服务
- 天气服务
程序启动时，会同时连接这 3 个服务，不用等一个连完再连下一个。这样启动速度更快。

### "动态工具注册"
MCP Server 连接成功后，会告诉 Client："我有这些工具可用"（工具名称、描述、参数格式）。
程序收到后， 自动把这些工具注册到工具注册表中 ，不需要手动写代码。

### "Header 环境变量鉴权透传"
有些 MCP Server 需要认证（比如搜索服务需要 API 密钥），认证信息通常放在 HTTP Header 里。

程序支持在配置文件中写类似这样的内容：
```
headers:
  Authorization: "Bearer $SEARCH_API_KEY"
```
启动时，程序会自动把 $SEARCH_API_KEY 替换成环境变量中的实际值，然后传递给 MCP Server。
这样用户不用把密钥写死在配置里，更安全。

### "实现远端工具/资源/Prompt 的热插拔扩展"
热插拔 = 不用重启程序，就能添加或移除工具。
因为 MCP 工具是动态注册的：
- 添加新工具：启动一个新的 MCP Server，程序会自动发现并注册它的工具
- 移除工具：关掉 MCP Server，程序会自动移除对应的工具
- 不需要改任何代码，不需要重新编译

### "MCP 工具自动注册为 mcp__server__tool 格式"
这是工具命名的约定：
- mcp ：表示这是一个 MCP 工具（不是内置工具）
- server ：MCP Server 的名字
- tool ：工具本身的名字

这样命名的好处是：
- 和内置工具区分开（内置工具没有 mcp__ 前缀）
- 一目了然知道是哪个 Server 提供的工具

### "无需修改核心即可接入搜索、文件系统等外部能力"
这是 MCP 的核心价值：

- 想接搜索？启动一个搜索 MCP Server 就行
- 想接文件系统？启动一个文件系统 MCP Server 就行
- 不需要改项目的核心代码
- 不需要重新编译
- 就像给电脑插一个 USB 设备，即插即用
