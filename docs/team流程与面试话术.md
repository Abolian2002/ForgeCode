# `/team` 多 Agent 团队模式流程说明

## 一、功能定位

`/team` 是面向复杂任务的一次性多 Agent 协作模式。它的核心目标是：当一个任务同时涉及分析、修改、测试、审查等多个维度时，不再让单个 Agent 串行完成全部工作，而是由一个主 Agent 先进行任务拆解，再调度多个子 Agent 分工协作，最后统一汇总结果交付给用户。

它适合处理这类任务：

- 任务范围较大，单 Agent 串行完成效率低
- 需要多个视角，例如实现、测试、审查、调研
- 可以按模块、文件、阶段或职责拆分
- 希望减少主上下文压力，避免长任务污染对话历史
- 希望一次输入后得到结构化的协作结果

一句话概括：`/team` 把“一个 Agent 从头做到尾”变成“主 Agent 组织多个子 Agent 分工完成一次复杂任务”。

---

## 二、整体流程

`/team` 的完整流程可以分为六个阶段：

```text
用户提出团队任务
    ↓
主 Agent 分析任务
    ↓
拆分子任务与分配子 Agent
    ↓
分阶段执行：并行 + 串行
    ↓
主 Agent 汇总、校验和冲突处理
    ↓
返回最终结果
```

---

## 三、阶段说明

### 1. 用户提出团队任务

用户通过 `/team` 输入一个相对复杂的任务，例如：

```text
/team 重构认证模块，补充测试，并检查是否存在安全风险
```

这个任务通常不是单一步骤，而是天然包含多个子目标：

- 理解现有认证模块
- 修改或重构相关逻辑
- 补充测试
- 检查安全问题
- 汇总最终结果

在普通模式下，这类任务往往需要用户多轮指挥；在 `/team` 中，用户只需要给出整体任务，后续由主 Agent 负责组织。

---

### 2. 主 Agent 分析任务

`/team` 启动后，主 Agent 会先扮演“项目经理 + 架构师”的角色，对任务进行分析，而不是马上执行。

这一阶段主要判断：

- 任务目标是什么
- 涉及哪些模块或文件范围
- 是否需要并行处理
- 哪些部分有依赖关系
- 哪些任务适合交给子 Agent
- 是否需要只读审查、测试验证或安全检查

主 Agent 的价值在于建立全局视角，避免多个子 Agent 各自为战。

---

### 3. 拆分子任务与分配子 Agent

分析完成后，主 Agent 会把大任务拆分成多个相对独立的子任务，并为每个子任务分配一个子 Agent。

子任务可以按不同方式拆分：

- 按模块拆分：认证模块、用户模块、配置模块分别处理
- 按职责拆分：一个负责实现，一个负责测试，一个负责审查
- 按阶段拆分：先调研，再修改，再验证
- 按风险拆分：高风险部分单独审查

每个子 Agent 都会拿到清晰的任务边界：

- 负责什么
- 不负责什么
- 需要产出什么
- 是否可以修改内容
- 是否只做分析或审查

这样可以让子 Agent 专注于自己的局部任务，减少上下文干扰。

---

### 4. 分阶段执行：并行 + 串行

`/team` 不是简单地把所有子 Agent 同时启动，而是根据任务依赖进行分阶段执行。

如果多个子任务互不依赖，可以并行执行。例如：

```text
阶段 1：并行分析不同模块
阶段 2：根据分析结果进行修改
阶段 3：测试 Agent 运行验证
阶段 4：审查 Agent 做最终检查
```

如果某个任务依赖前一个任务的结果，就需要串行执行。例如测试必须在代码修改之后进行，审查也通常需要在主要修改完成后进行。

这种“并行 + 串行”的设计兼顾了效率和正确性：

- 无依赖任务并行，提高速度
- 有依赖任务串行，保证顺序
- 主 Agent 统一控制阶段边界，减少冲突

---

### 5. 子 Agent 独立执行

每个子 Agent 都在相对独立的上下文中执行自己的任务。

这样做有几个好处：

- 避免所有细节都堆到主上下文中
- 子 Agent 可以专注于局部问题
- 不同任务之间减少互相干扰
- 主 Agent 只需要接收结构化结果，而不是承担全部细节

子 Agent 完成后，会向主 Agent 返回自己的结果，例如：

- 做了哪些分析
- 修改了哪些内容
- 发现了哪些问题
- 哪些地方需要后续处理
- 是否存在失败或阻塞

---

### 6. 主 Agent 汇总、校验和冲突处理

子 Agent 执行结束后，主 Agent 会重新回到中心位置，负责把多个结果整合成一个一致的交付。

这一阶段会重点处理：

- 不同子 Agent 的结果是否冲突
- 是否有重复修改或遗漏任务
- 测试或验证是否通过
- 审查意见是否需要修复
- 最终结果是否满足用户最初的目标

如果发现某个子任务失败，主 Agent 可以决定：

- 重试该子任务
- 调整任务边界后再执行
- 降级为人工说明
- 在最终报告中明确风险

主 Agent 最后不会简单拼接子 Agent 的输出，而是给用户一个经过整理的最终结果。

---

## 四、用户视角下的体验

用户使用 `/team` 时，体验应该是这样的：

1. 我提出一个复杂任务，不需要手动拆给不同角色
2. 主 Agent 会自动分析任务并组织多个子 Agent
3. 子 Agent 分别处理不同部分，彼此上下文隔离
4. 主 Agent 汇总结果，处理冲突和遗漏
5. 我最终收到一份结构化交付，而不是多个零散答案

它本质上让 AI 从“单人助手”变成“由一个负责人组织的小团队”。

---

## 五、为什么需要 `/team`

单 Agent 在小任务上足够好，但面对复杂工程任务时会有几个明显问题：

- 所有工作串行完成，效率较低
- 一个上下文里混杂分析、实现、测试、审查，信息噪声高
- 一个 Agent 同时承担多个角色，容易顾此失彼
- 长任务中上下文压力变大，前期决策容易被淹没
- 缺少明确的分工和阶段边界

`/team` 通过多 Agent 协作解决这些问题：

- 用主 Agent 统一规划，保证全局方向
- 用子 Agent 分工执行，提高并行度
- 用上下文隔离降低噪声
- 用阶段调度处理依赖关系
- 用汇总审查保证最终交付一致

## 六、与普通模式和 `/goal` 模式的区别

### 普通模式

普通模式适合短任务和即时交互。用户给一个问题，系统执行一轮并返回结果。它灵活、轻量，但不适合拆分复杂任务。

### `/team` 模式

`/team` 适合一次复杂协作。它强调“分工”：主 Agent 负责组织，子 Agent 负责局部任务，最后统一汇总。它通常是一次启动、一次协作、一次交付。

### `/goal` 模式

`/goal` 适合长时间持续推进。它强调“长期目标”：系统会围绕一个目标持续执行、反思、保存进度，直到完成或退出。

三者可以这样理解：

```text
普通模式：一个助手解决一个问题
/team 模式：一个负责人组织小团队完成一次复杂任务
/goal 模式：一个长期执行器持续推进一个目标
```

## 七、关键设计思想

### 1. 主 Agent 负责全局，子 Agent 负责局部

主 Agent 不应该陷入所有细节，而是负责拆分、调度、汇总和决策。子 Agent 则专注处理明确边界内的任务。

### 2. 子 Agent 是任务驱动的，不是固定角色

子 Agent 不一定永远是“测试专家”或“审查专家”，而是根据当前任务动态创建。任务需要什么能力，就生成什么样的执行单元。

### 3. 并行不是无脑并行，必须尊重依赖

能并行的任务并行执行，有前后依赖的任务串行执行。这样既提升效率，又避免顺序错误。

### 4. 上下文隔离是多 Agent 的核心价值

每个子 Agent 有自己的上下文，可以避免把所有分析、尝试、错误和中间结论堆到主对话里，主 Agent 只保留高价值摘要和最终决策。

### 5. 最终交付必须由主 Agent 统一收口

多 Agent 的输出不能直接原样拼接，否则会出现重复、冲突和风格不一致。必须由主 Agent 做最后的整合、校验和解释。

## 八、一次典型 `/team` 协作示例

假设用户输入：

```text
/team 为用户认证模块补齐测试，并检查潜在安全问题
```

一次合理的团队流程可能是：

```text
1. 主 Agent 分析任务范围：认证模块、登录逻辑、权限校验、测试目录
2. 创建子 Agent A：阅读认证模块并总结关键逻辑
3. 创建子 Agent B：补充缺失测试
4. 创建子 Agent C：只读审查安全风险
5. 子 Agent A/B/C 分阶段执行
6. 主 Agent 汇总测试结果和安全意见
7. 如果测试失败，安排修复或说明原因
8. 返回最终交付：完成内容、验证结果、风险点、后续建议
```

这个流程体现了 `/team` 的核心优势：不同 Agent 做不同事情，主 Agent 负责把结果组织成一个完整答案。

## 九、1-2 分钟面试话术

面试官您好，我来介绍一下我设计的 `/team` 多 Agent 团队模式。

这个能力主要解决的是单 Agent 在复杂工程任务里的瓶颈。普通模式下，一个 Agent 要同时做需求分析、代码修改、测试和审查，所有事情都串行完成，效率低，而且上下文会越来越嘈杂。所以我设计了 `/team`，让用户通过一个命令主动触发团队协作，由主 Agent 负责全局规划和调度，多个子 Agent 负责具体子任务，最后再由主 Agent 汇总交付。

它的流程分成几步。第一步，用户输入一个复杂任务；第二步，主 Agent 先分析任务目标、范围和依赖关系；第三步，把任务拆成多个子任务，并为每个子任务创建对应的子 Agent；第四步，根据依赖关系分阶段执行，能并行的并行，有前后顺序的串行；第五步，子 Agent 返回各自结果；最后由主 Agent 做统一汇总、冲突处理、验证结果整理，并给用户一个结构化交付。

这里我认为最关键的设计点有三个。第一，主 Agent 和子 Agent 的职责要分清，主 Agent 负责全局和收口，子 Agent 负责局部执行。第二，子 Agent 不是固定角色，而是任务驱动动态创建，这样可以适配不同场景。第三，多 Agent 的价值不只是并行，更重要的是上下文隔离，让每个 Agent 专注自己的任务，避免主上下文被大量中间信息污染。

和普通模式相比，`/team` 更适合一次性复杂协作；和 `/goal` 相比，`/team` 更强调分工和阶段交付，而不是长时间持续运行。整体上，它把 AI 从一个单人助手扩展成了一个由主 Agent 统一协调的小型工程团队。
