好问题，这是一个很通用的 LLM 应用架构问题，面试很容易问。系统梳理一下：

## 一、噪声干扰的常见原因与解决方案

### 什么是"噪声干扰"

模型上下文中存在**与当前任务无关或低相关的信息**，导致模型：
- 注意力分散，抓不住重点
- 产生幻觉（被无关信息误导）
- 回答质量下降，甚至答非所问

### 原因 1：长对话历史累积

- **问题**：对话越聊越长，前面聊过的 A/B/C 话题和当前聊的 D 话题混在一起
- **解决**：
  - **摘要压缩**：定期把历史对话总结成摘要，保留关键信息
  - **滑动窗口**：只保留最近 N 轮对话，更早的丢掉或摘要
  - **主题切换检测**：检测到用户换了话题，重置或压缩历史

### 原因 2：RAG 检索返回过多不相关文档

- **问题**：用户问一个问题，RAG 检索回来 10 篇文档，其中只有 2 篇相关，8 篇是噪声
- **解决**：
  - **重排序（Rerank）**：先用 embedding 粗召回，再用交叉编码器精排，只保留 top-k 相关的
  - **分块策略优化**：按语义分块（不是按字符数硬切），减少 chunk 内无关内容
  - **多跳检索**：复杂问题拆成多个子问题分别检索，再合并
  - **查询改写**：先让模型改写用户查询，用改写后的 query 去检索

### 原因 3：工具调用结果冗余

- **问题**：工具返回了大量数据（比如 grep 返回 100 行结果、read_file 返回整个文件），其中大部分没用
- **解决**：
  - **结果截断 + 提示**：超长结果只返回前 N 行，告诉模型"结果已截断，需要更精确搜索"
  - **分页/滚动查询**：工具支持分页参数，模型按需翻页，不一次性返回全部
  - **结构化输出**：工具不是返回原始文本，而是返回结构化的 JSON，模型更容易解析

### 原因 4：系统提示词过于冗长

- **问题**：系统提示词塞了一堆规则、约束、示例，大部分和当前任务无关
- **解决**：
  - **动态系统提示词**：根据当前任务类型动态选择注入哪些规则，不是全量注入
  - **规则分类存储**：把规则按领域分类，需要哪个领域的就加载哪个领域的
  - **Few-shot 示例按需注入**：不是把所有示例都放进去，而是根据任务类型选最相关的 1-2 个

### 原因 5：多模态输入的噪声

- **问题**：给模型一张图片，但图片里大部分区域和问题无关（比如一张截图里有大量无关 UI 元素）
- **解决**：
  - **图像裁剪 / 聚焦**：先检测关键区域，只把相关区域传给模型
  - **OCR 后过滤**：从图片提取文字后，做关键词过滤再给模型

## 二、Token 成本过高的常见原因与解决方案

### 原因 1：上下文窗口越来越大，习惯性全量塞

- **问题**：模型支持 128k、200k 甚至 1M 的上下文，开发者图省事把所有内容全塞进去
- **解决**：
  - **按需加载**：需要什么拿什么，不是全量准备好
  - **分层上下文**：摘要层 + 详细层，先看摘要，需要细节再展开
  - **上下文预算管理**：设置一个 Token 预算上限，超过就触发压缩

### 原因 2：长文档/长代码全量输入

- **问题**：用户说"分析这个项目"，你把整个项目几十上百个文件全读了塞进去
- **解决**：
  - **代码地图（Code Map）**：先生成项目的结构摘要（文件列表、函数签名、类定义），模型根据摘要决定读哪些文件
  - **增量读取**：模型先读目录，选几个文件读，读了之后决定再读哪些，一步步深入
  - **AST 提取**：对代码用 AST 提取关键结构（函数签名、类型定义），去掉函数体，大幅减少 Token

### 原因 3：重复调用相同或相似查询

- **问题**：同一个问题反复问，或者多个用户问几乎一样的问题，每次都重新调用模型
- **解决**：
  - **Prompt Cache**：相同或相似的 system prompt + history 复用缓存（Anthropic Prompt Caching、OpenAI Caching）
  - **语义缓存（Semantic Cache）**：用户输入做 embedding，相似问题直接返回之前的答案，不调模型
  - **结果缓存**：工具调用结果缓存，相同参数的工具调用直接返回缓存结果

### 原因 4：大模型小用

- **问题**：简单的分类、提取、格式化任务也用最贵的大模型
- **解决**：
  - **模型路由**：根据任务难度选模型——简单任务用小模型（gpt-4o-mini、Haiku），复杂任务用大模型（Sonnet、GPT-4o）
  - **流水线设计**：先用小模型做预处理（分类、提取、过滤），关键步骤再用大模型

### 原因 5：输出 Token 浪费

- **问题**：模型回答太啰嗦，或者输出了大量不需要的格式（比如多余的解释、Markdown 装饰）
- **解决**：
  - **明确输出格式**：在提示词里严格规定输出格式（JSON Schema、字数限制）
  - **结构化输出**：让模型直接返回 JSON，减少自然语言的冗余
  - **短输出模式**：简单任务明确要求"只回答结果，不要解释"

### 原因 6：多轮对话中历史重复

- **问题**：多轮对话中，系统提示词每轮都重复发、之前的工具结果每轮都带着
- **解决**：
  - **Prompt Cache 复用**：利用模型厂商的缓存能力，相同的 system prompt 和历史只计费一次
  - **工具结果占位**：已经展示给用户、模型后续不需要参考的工具结果，清理掉内容只保留占位标记

## 三、总结：通用方法论

| 策略类型 | 核心思想 | 典型技术 |
|---------|---------|---------|
| **选什么进上下文** | 只带需要的，不带全量 | RAG检索+重排序、动态提示词、代码地图、增量读取 |
| **怎么压缩上下文** | 保留语义，减少体积 | 摘要压缩、滑动窗口、结果截断、AST提取 |
| **怎么复用计算** | 同样的东西不花钱算第二次 | Prompt Cache、语义缓存、结果缓存 |
| **怎么选模型** | 多大的碗盛多少饭 | 模型路由、大小模型分层、简单任务用小模型 |
| **怎么结构化** | 减少自然语言的水分 | JSON Schema 输出、结构化工具返回、格式约束 |

面试的时候如果被问到，可以从这五个维度展开，每个维度说 1-2 个具体技术和适用场景，就很稳了。
