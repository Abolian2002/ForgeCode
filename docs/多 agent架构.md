## 多 Agent 架构 — 面试要点总结

### 1. 什么是多 Agent 架构

把复杂任务拆分给多个专门的 Agent，每个 Agent 负责一个领域，协作完成任务。

类比软件开发团队：产品经理（需求分析）→ 架构师（系统设计）→ 工程师（编码）→ 测试（验证）。单 Agent 像一个人包办所有，多 Agent 像团队分工协作。

---

### 2. Agent 的边界是什么

每个 Agent 的职责范围和能力限制，包含五个维度：

| 维度 | 说明 | 示例 |
|------|------|------|
| **角色定位** | 干什么的 | 代码审查 Agent、测试编写 Agent |
| **工具集** | 能用哪些工具 | 审查 Agent 只能读文件，不能写文件 |
| **权限范围** | 能操作哪些资源 | 只能访问 src/ 目录 |
| **知识范围** | 了解哪些信息 | 前端 Agent 只懂 React |
| **输出格式** | 返回什么类型结果 | 生成 Agent 返回代码，审查 Agent 返回问题列表 |

**为什么需要边界**：安全性（防止恶意操作扩散）、专业性（专注一个领域）、可维护性（修改一个不影响其他）、可追溯性（出问题知道是谁干的）。

---

### 3. 谁来调度

#### 模式一：中心化调度（最常见）
- 有一个**主 Agent（Master Agent）**负责：接收请求 → 拆分任务 → 分配给子 Agent → 收集结果 → 汇总返回
- 优点：结构清晰、统一决策；缺点：单点瓶颈

#### 模式二：去中心化调度
- 没有主 Agent，多个 Agent 自主协商，通过消息传递协作
- 优点：容错性好；缺点：协调成本高、易冲突

#### 常见调度模式
| 模式 | 说明 | 场景 |
|------|------|------|
| **流水线** | A→B→C 串行执行 | 需求分析→设计→编码→测试 |
| **并行** | A 和 B 同时执行 | 前后端同时开发 |
| **轮询** | 每个 Agent 轮流尝试 | 不确定谁能解决 |
| **投票** | 多 Agent 投票选最优 | 方案决策 |

---

### 4. 中间状态存在哪里

#### 方式一：共享存储（最常见）
- 所有 Agent 都能读写的公共数据仓库（数据库、文件系统、专门服务）
- 优点：统一管理；缺点：可能成为性能瓶颈

#### 方式二：消息传递（事件驱动）
- 发布/订阅或请求/响应模式，不持久化
- 优点：解耦性好；缺点：消息可能丢失

#### 方式三：上下文传递（链式）
- 上一个 Agent 的输出直接作为下一个 Agent 的输入
- 优点：简单直接；缺点：只能串行

#### 实际项目中通常是混合模式
```
主 Agent 拆分任务 → 写入共享存储
    ├─→ Agent A 读取执行 → 结果写入共享存储
    ├─→ Agent B 读取执行 → 结果写入共享存储
    └─→ Agent C 读取执行 → 结果写入共享存储
主 Agent 收集结果 → 汇总返回
```

---

### 5. 异常怎么处理

#### 单个 Agent 失败
| 策略 | 适用场景 |
|------|---------|
| **重试** | 网络抖动、临时故障（≤3次） |
| **降级** | Agent A 挂了，用 Agent B 代替 |
| **跳过** | 非关键任务失败 |
| **回滚** | 事务性任务，必须全部成功或全部失败 |

#### Agent 之间的冲突（如同时修改同一文件）
| 策略 | 说明 |
|------|------|
| **乐观锁** | 修改前检查版本号 |
| **悲观锁** | 修改前先加锁 |
| **仲裁** | 交给主 Agent 判断 |
| **投票** | 多 Agent 投票决定 |

#### 死锁（互相等待）
- 设置超时时间，超时后强制取消
- 避免循环依赖
- 死锁检测算法自动打破

#### 结果不一致（不同 Agent 给出矛盾结论）
- 主 Agent 判断
- 多 Agent 投票
- 引入人类审核

#### 全局异常处理流程
```
失败 → 重试 ≤ 3次？
    ├─→ 是 → 重新执行
    └─→ 否 → 有关键任务依赖？
              ├─→ 是 → 回滚所有操作，通知用户
              └─→ 否 → 标记失败，继续其他任务，最后汇总说明
```

---

### 总结

| 问题 | 回答 |
|------|------|
| **什么是多 Agent** | 多个专门 Agent 分工协作完成复杂任务 |
| **边界是什么** | 角色定位、工具集、权限范围、知识范围、输出格式 |
| **谁来调度** | 中心化（主 Agent 统一调度）或去中心化（自主协商） |
| **中间状态在哪里** | 共享存储、消息传递、上下文传递，通常混合使用 |
| **异常怎么处理** | 重试/降级/跳过/回滚；冲突用锁或仲裁；死锁用超时检测；不一致用投票或人类审核 |

这个项目 不是 Web 后端服务 ，所以没有用 Axum、Actix 这些 Web 框架。
## 它是什么类型的应用
这是一个 本地终端应用（CLI + TUI） ，在用户电脑上直接运行，不是部署在服务器上提供 HTTP API 的服务。
## 一句话总结
这个项目是一个 本地运行的终端 AI Agent 工具 ，用 Tokio 异步运行时 + reqwest HTTP 客户端 + Ratatui TUI 渲染，不需要 Web 后端框架，因为它不是 Web 服务。
