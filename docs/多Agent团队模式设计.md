# MiniCode 多 Agent 团队模式设计文档

## 一、设计背景与目标

### 1.1 背景

MiniCode 当前采用单 Agent 架构，通过 `model → tool → model` 循环完成代码编写、调试、重构等任务。单 Agent 在简单任务上表现良好，但在**大型、复杂、多领域的任务**上存在瓶颈：

- **效率瓶颈**：单 Agent 串行执行，大任务耗时长
- **专业深度**：一个 Agent 既要写代码又要写测试还要做审查，精力分散
- **上下文污染**：长对话下上下文积累过多，模型容易"遗忘"早期决策
- **角色模糊**：单一角色难以兼顾编码、测试、审查等不同思维模式

### 1.2 参考设计：Claude Code Sub-agents

本设计参考了 Claude Code 的 Sub-agents 架构，核心思想：

| 特性 | Claude Code | MiniCode（我们的设计） |
|------|-------------|----------------------|
| **子 Agent 定义** | Markdown + YAML frontmatter，可配置 | 动态创建 + 模板化，可配置 |
| **上下文隔离** | 每个子 Agent 独立上下文窗口 | 每个子 Agent 独立上下文窗口 |
| **工具权限** | 按子 Agent 配置可用工具 | 按任务分配可用工具 |
| **调用方式** | 自动选择 / 显式调用 / 链式调用 | 主 Agent 动态调度 |
| **最大并行数** | 异步模式支持 100+ | 最多 5 个（成本控制） |
| **可恢复性** | 支持 resume 恢复子 Agent | 支持续轮继续 |

### 1.3 目标

在单 Agent 架构基础上，增加**多 Agent 团队协作模式（Team Mode）**：

- 用户通过 `/team` 命令主动触发
- 主 Agent 负责分析、任务分解、动态创建子 Agent、调度、汇总
- 子 Agent 是**任务驱动的动态实体**，不是固定角色
- 复用现有基础设施（工具注册表、上下文压缩、权限系统、MCP 接入）

### 1.4 设计原则

| 原则 | 说明 |
|------|------|
| **用户主动触发** | 多 Agent 模式仅在用户明确要求时启动，不自动启用 |
| **中心化调度** | 主 Agent 统一调度，子 Agent 不直接通信 |
| **任务驱动** | 子 Agent 是动态创建的，每个子 Agent 对应一个具体任务 |
| **上下文隔离** | 每个子 Agent 有独立上下文，避免污染主对话 |
| **最大化复用** | 复用单 Agent 的所有基础设施，不重复造轮子 |
| **安全可控** | 子 Agent 的所有操作都经过权限审查，工具权限按需分配 |
| **渐进式实现** | 从最小可用版本开始，逐步增加功能 |

## 二、整体架构

### 2.1 架构总览

```
用户输入：/team "重构项目错误处理，统一用 anyhow，并补充单元测试"
    │
    ▼
┌──────────────────────────────────────────────────────────────┐
│                    主 Agent (Orchestrator)                   │
│  角色：项目经理 + 架构师                                      │
│  职责：分析项目、任务分解、动态创建子Agent、调度、汇总、冲突解决 │
│  子Agent上限：5个（由主Agent分析后决定数量）                    │
└──────────────────────────┬───────────────────────────────────┘
                           │
                           ▼
              ┌────────────────────────┐
              │     任务计划（核心）     │
              │  · 子任务列表            │
              │  · 每个子任务的配置      │
              │  · 依赖关系              │
              │  · 执行阶段划分          │
              └───────────┬────────────┘
                          │
         ┌────────────────┼────────────────┐
         ▼                ▼                ▼
   ┌─────────┐      ┌─────────┐      ┌─────────┐
   │ 子Agent 1│      │ 子Agent 2│      │ 子Agent 3│
   │ 任务A    │      │ 任务B    │      │ 任务C    │
   │ 读写权限 │      │ 读写权限 │      │ 只读权限 │
   └────┬────┘      └────┬────┘      └────┬────┘
        │                 │                 │
        └─────────────────┼─────────────────┘
                          ▼
                共享文件系统 + 共享工具集
                （子 Agent 通过文件间接共享状态）

执行流程：主Agent分析 → 生成任务计划 → 分阶段执行（并行+串行） → 主Agent总结修改 → 返回用户
（单轮执行，单个子Agent失败可重试1-2次）
```

### 2.2 核心概念

| 概念 | 说明 |
|------|------|
| **主 Agent** | Orchestrator，负责任务分解、动态创建子 Agent、调度、汇总的核心 Agent |
| **子 Agent** | Worker，执行具体子任务的 Agent，**动态创建**，每个对应一个具体任务 |
| **子 Agent 模板** | 预定义的子 Agent 配置（系统提示词、工具权限、模型选择），可复用 |
| **任务** | 主 Agent 分解后分配给子 Agent 的工作单元 |
| **任务计划** | 主 Agent 生成的完整任务分解 + 子 Agent 配置 + 依赖关系 + 执行阶段 |
| **执行阶段** | 任务按依赖关系分组，同一阶段内的任务可并行执行 |
| **团队会话** | 一次多 Agent 协作的完整过程，包含主 Agent 和所有子 Agent |

### 2.3 子 Agent 的本质：不是固定角色，而是任务执行单元

**关键转变**：从"固定角色的子 Agent"转变为"任务驱动的动态子 Agent"。

| 维度 | 旧设计（固定角色） | 新设计（任务驱动） |
|------|-------------------|-------------------|
| **子 Agent 类型** | 写死3种（修改/测试/审查） | **动态创建**，每个子 Agent 有自定义的任务描述、工具权限、系统提示词 |
| **子 Agent 数量** | 主 Agent 决定（最多5个） | 主 Agent 决定（最多5个） |
| **边界划分** | 按角色划分 | **按任务/文件/模块划分** |
| **执行方式** | 全部并行 | **有依赖的串行，无依赖的并行** |
| **子 Agent 通信** | 不通信，主 Agent 汇总 | **通过文件系统间接共享**，主 Agent 协调 |
| **可复用性** | 角色固定，复用性差 | 模板化定义，可跨任务复用 |

### 2.4 与单 Agent 的关系

```
普通模式（单 Agent）        团队模式（多 Agent）
     │                            │
     ├─ 工具注册表                ├─ 工具注册表（复用）
     ├─ Agent Loop               ├─ Agent Loop（复用）
     ├─ 上下文压缩                ├─ 上下文压缩（复用，每个 Agent 独立）
     ├─ 权限系统                 ├─ 权限系统（复用，按任务分配）
     ├─ MCP 接入                 ├─ MCP 接入（复用）
     ├─ Skill 系统               ├─ Skill 系统（复用，按任务加载）
     │                            │
     └─ 单一会话上下文            └─ 主 Agent 上下文 + 多个子 Agent 上下文
```

**关键：多 Agent 模式不是重新造轮子，而是在单 Agent 基础上增加一层调度逻辑。**

## 三、子 Agent 配置与定义

### 3.1 子 Agent 的配置结构

每个子 Agent 是一个独立配置的执行单元，包含以下配置项：

```yaml
子 Agent 配置:
  name: "auth-module-refactor"           # 唯一标识，小写字母+连字符
  description: "重构 auth 模块的错误处理"  # 任务描述
  system_prompt: |                        # 系统提示词（定义角色和行为）
    你是一个高级软件工程师，专注于 Rust 项目的错误处理重构。
    你的任务是将 src/auth/ 目录下的所有错误处理从 match 风格改为 anyhow::Result。
    要求：
    1. 保持功能不变
    2. 遵循项目编码规范
    3. 修改后确保 cargo check 通过
    
  tools:                                  # 允许使用的工具列表
    - list_files
    - read_file
    - grep_files
    - edit_file
    - run_command                         # 仅允许 cargo check
    
  model: "inherit"                        # 模型选择：inherit / sonnet / opus / haiku
  working_directory: "src/auth/"          # 工作目录限制（可选）
  max_steps: 50                           # 最大执行步数（防止无限循环）
```

### 3.2 子 Agent 模板（可复用）

为了提高效率，可以预定义常用的子 Agent 模板。主 Agent 可以基于模板快速创建子 Agent，只需修改任务描述即可。

#### 模板1：代码修改专家

```yaml
模板名称: code-modifier
描述: 通用的代码修改专家，适用于各种编码任务
系统提示词: |
  你是一个高级软件工程师。你的任务是根据任务描述修改代码。
  要求：
  1. 仔细阅读相关文件，理解现有逻辑
  2. 遵循项目的编码规范和最佳实践
  3. 修改后确保代码能编译通过
  4. 保持代码简洁、可读
允许的工具: [list_files, read_file, grep_files, glob, edit_file, write_file, run_command]
默认模型: inherit
```

#### 模板2：测试专家

```yaml
模板名称: test-expert
描述: 测试工程师，负责编写和运行测试
系统提示词: |
  你是一个测试工程师。你的任务是编写测试用例、运行测试、确保代码质量。
  要求：
  1. 理解被测试代码的功能
  2. 编写全面的单元测试和集成测试
  3. 确保所有测试通过
  4. 遵循项目的测试规范
允许的工具: [list_files, read_file, grep_files, glob, edit_file, write_file, run_command]
默认模型: inherit
```

#### 模板3：代码审查员

```yaml
模板名称: code-reviewer
描述: 代码审查员，只读权限，负责审查代码质量
系统提示词: |
  你是一个严格的代码审查员。你的职责是审查代码修改的质量。
  检查维度：
  1. 正确性：逻辑是否正确
  2. 安全性：是否有安全漏洞
  3. 性能：是否有性能问题
  4. 可读性：代码是否清晰易读
  5. 规范性：是否符合项目规范
  
  你只能读取文件，不能修改。给出结构化的审查意见。
允许的工具: [list_files, read_file, grep_files, glob]
默认模型: inherit
```

#### 模板4：调试专家

```yaml
模板名称: debugger
描述: 调试专家，负责定位和修复错误
系统提示词: |
  你是一个调试专家。你的任务是定位和修复代码中的错误。
  调试流程：
  1. 理解错误信息和堆栈跟踪
  2. 复现问题
  3. 定位根本原因
  4. 实施最小化修复
  5. 验证修复有效
允许的工具: [list_files, read_file, grep_files, glob, edit_file, run_command]
默认模型: inherit
```

### 3.3 模板的使用方式

主 Agent 创建子 Agent 时：

1. **选择模板**：从预定义模板中选择合适的模板
2. **定制化**：修改任务描述、调整工具权限、指定工作目录等
3. **创建子 Agent**：基于定制后的配置启动子 Agent

**例子**：
```
主 Agent 分析任务：需要修改 auth 模块和 api 模块的错误处理

创建子 Agent 1（基于 code-modifier 模板）：
  - name: auth-refactor
  - 任务：重构 src/auth/ 目录下的错误处理
  - 工作目录：src/auth/

创建子 Agent 2（基于 code-modifier 模板）：
  - name: api-refactor
  - 任务：重构 src/api/ 目录下的错误处理
  - 工作目录：src/api/

创建子 Agent 3（基于 test-expert 模板）：
  - name: run-tests
  - 任务：运行所有测试，确保修改不破坏功能
  - 依赖：[auth-refactor, api-refactor]
```

### 3.4 工具权限控制

**最小权限原则**：每个子 Agent 只拥有完成任务所需的最少工具权限。

| 任务类型 | 推荐工具权限 | 说明 |
|---------|------------|------|
| **代码审查** | 只读工具（list/read/grep/glob） | 不能修改任何东西 |
| **文档编写** | 读工具 + 写工具（仅限文档目录） | 不能运行命令 |
| **代码修改** | 读工具 + 写工具 + 构建命令 | 不能运行危险命令 |
| **测试** | 读工具 + 写工具（仅限测试文件） + 测试命令 | 不能修改生产代码 |
| **调试** | 读工具 + 写工具 + 各种命令 | 需要更灵活的权限 |

**为什么要限制工具权限？**
- **安全性**：防止子 Agent 误操作或越权操作
- **聚焦性**：减少子 Agent 的选择空间，让它更专注于任务
- **可预测性**：知道子 Agent 能做什么、不能做什么

## 四、工作流程

### 4.1 完整流程

```
阶段0：触发
  │
  ├─ 用户输入 /team "任务描述"
  ├─ 或在对话中说"用多 Agent 模式做 XXX"
  │
  ▼
阶段1：分析（主 Agent）
  │
  ├─ 主 Agent 使用工具（list_files/read_file/grep）快速扫描项目
  ├─ 理解代码结构、依赖关系和任务范围
  └─ 完成分析，准备生成任务计划
  │
  ▼
阶段2：生成任务计划（主 Agent）
  │
  ├─ 决定子 Agent 数量（最多5个）
  ├─ 分解为独立的子任务
  ├─ 为每个子任务选择模板 + 定制配置
  ├─ 定义依赖关系
  ├─ 划分执行阶段
  └─ 生成完整任务计划
  │
  ▼
阶段3：任务计划确认（可选）
  │
  ├─ 主 Agent 将任务计划展示给用户
  ├─ 用户确认 / 修改 / 取消
  └─ 用户确认后进入执行阶段
  │
  ▼
阶段4：分阶段执行（子 Agent，单轮）
  │
  ├─ 按阶段顺序执行
  │    │
  │    ├─ 阶段1：并行执行无依赖的子任务
  │    │    ├─ 子 Agent A 执行（修改 auth 模块）
  │    │    ├─ 子 Agent B 执行（修改 api 模块）
  │    │    └─ 单个失败 → 重试1-2次
  │    │
  │    ├─ 阶段2：执行依赖阶段1的子任务
  │    │    └─ 子 Agent C 执行（运行测试）
  │    │
  │    └─ 阶段3：执行依赖阶段2的子任务
  │         └─ 子 Agent D 执行（代码审查）
  │
  └─ 所有阶段完成后进入汇总阶段
  │
  ▼
阶段5：汇总输出（主 Agent）
  │
  ├─ 主 Agent 整合所有子任务结果
  ├─ 解决冲突（如有）
  ├─ 主 Agent 做最终修改和完善
  ├─ 生成最终报告，列出所有修改的文件
  └─ 返回给用户
  │
  ▼
阶段6：用户手动续轮（可选）
  │
  ├─ 用户对结果不满意 → 输入 /team:continue "继续修改XXX"
  ├─ 主 Agent 基于上一轮结果继续执行
  └─ 进入阶段1重新分析（或阶段4直接执行）
```

**关键设计**：
- **分析与计划分离**：先分析项目，再生成任务计划
- **任务驱动**：子 Agent 是动态创建的，每个对应一个具体任务
- **分阶段执行**：有依赖的串行，无依赖的并行
- **单轮执行**：一次用户提问，主 Agent → 子 Agent 分阶段执行 → 主 Agent 总结修改 → 返回用户
- **单个子 Agent 失败可重试**：同一轮内，单个子 Agent 执行失败，主 Agent 可重试1-2次
- **用户手动续轮**：默认单轮，用户对结果不满意可手动触发 `/team:continue` 继续下一轮

### 4.2 任务计划结构

```yaml
任务计划:
  任务ID: team-task-001
  原始需求: "重构项目错误处理，统一用 anyhow，并补充单元测试"
  子Agent数量: 4（由主Agent分析后决定，最多5个）
  执行模式: 单轮（用户可手动续轮）
  
  子任务列表:
    - 子任务ID: T1
      name: "auth-module-refactor"
      模板: code-modifier
      描述: 重构 src/auth/ 目录下的错误处理，统一用 anyhow
      允许的工具: [list_files, read_file, grep_files, edit_file, run_command]
      工作目录: src/auth/
      依赖: []
      输出: 修改后的文件列表
      
    - 子任务ID: T2
      name: "api-module-refactor"
      模板: code-modifier
      描述: 重构 src/api/ 目录下的错误处理，统一用 anyhow
      允许的工具: [list_files, read_file, grep_files, edit_file, run_command]
      工作目录: src/api/
      依赖: []
      输出: 修改后的文件列表
      
    - 子任务ID: T3
      name: "unit-tests"
      模板: test-expert
      描述: 为 auth 和 api 模块补充单元测试
      允许的工具: [list_files, read_file, grep_files, edit_file, write_file, run_command]
      工作目录: tests/
      依赖: [T1, T2]
      输出: 新增的测试文件 + 测试结果
      
    - 子任务ID: T4
      name: "code-review"
      模板: code-reviewer
      描述: 审查所有修改的代码质量
      允许的工具: [list_files, read_file, grep_files, glob]
      依赖: [T1, T2, T3]
      输出: 审查意见报告
  
  执行阶段:
    - 阶段1（并行）: [T1, T2]    # 两个模块可以并行修改
    - 阶段2（串行）: [T3]         # 测试依赖修改完成
    - 阶段3（串行）: [T4]         # 审查依赖所有修改完成
```

### 4.3 子任务的边界划分策略

主 Agent 划分任务时，遵循以下原则：

#### 策略1：按文件/模块划分（最常用，可并行）

```
任务：重构项目错误处理
├─ 子任务1：src/auth/ 目录
├─ 子任务2：src/api/ 目录
├─ 子任务3：src/utils/ 目录
└─ 子任务4：运行测试（依赖以上所有）
```

**适用场景**：各模块独立，修改互不干扰
**优点**：完全并行，效率高
**注意**：避免多个子任务修改同一个文件

#### 策略2：按任务类型划分（有依赖，串行+并行）

```
任务：新功能开发
├─ 阶段1：代码实现（可按模块并行）
│    ├─ 子任务1：后端 API 实现
│    └─ 子任务2：前端页面实现
│
├─ 阶段2：测试（串行）
│    └─ 子任务3：编写集成测试
│
└─ 阶段3：审查（串行）
     └─ 子任务4：代码审查
```

**适用场景**：有明确的先后依赖关系
**优点**：逻辑清晰，符合开发流程

#### 策略3：混合模式

根据实际任务灵活组合以上两种策略。

### 4.4 子 Agent 数量的决策逻辑

主 Agent 根据以下因素决定子 Agent 数量（最多5个）：

| 因素 | 说明 |
|------|------|
| **任务复杂度** | 任务越复杂，子 Agent 越多 |
| **可并行度** | 能拆成多少独立子任务 |
| **文件数量** | 需要修改多少文件 |
| **模块数量** | 涉及多少个独立模块 |
| **任务类型多样性** | 是否需要不同专业技能（编码/测试/审查） |

**决策示例**：
- 简单修改（1个文件）→ 1个子 Agent
- 重构一个模块 → 2-3个子 Agent（修改 + 测试 + 审查）
- 多模块重构 → 3-5个子 Agent（按模块拆分 + 测试 + 审查）

## 五、通信机制与子 Agent 边界

### 5.1 通信原则

- **中心化通信**：所有通信通过主 Agent 中转
- **子 Agent 不直接通信**：避免混乱和冲突
- **通过文件系统间接共享**：子 Agent 都操作同一个项目目录，通过文件共享状态
- **消息驱动**：主 Agent 通过消息分配任务、收集结果

### 5.2 为什么子 Agent 不直接通信？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **直接通信** | 灵活性高 | 协调复杂、容易死锁、调试困难、不可控 |
| **中心化调度（我们选这个）** | 简单可控、易于调试、冲突可集中解决 | 主 Agent 可能成为瓶颈（但5个子 Agent 不是问题） |

**结论**：对于最多5个子 Agent 的规模，中心化调度完全够用，而且简单可靠。

### 5.3 子 Agent 通过文件系统间接共享

子 Agent 之间虽然不直接通信，但它们共享同一个文件系统，可以通过文件间接共享状态：

```
子 Agent A 修改 src/auth/mod.rs
    │
    └─ 文件系统中留下修改后的文件
         │
         └─ 子 Agent B（测试）读取 src/auth/mod.rs，基于修改后的代码写测试
```

**注意事项**：
- 有依赖关系的子任务必须分阶段执行（先修改后测试）
- 同一阶段内的子任务不能修改同一个文件（避免冲突）
- 文件锁机制作为兜底保障

### 5.4 消息类型

| 消息 | 发送者 | 接收者 | 内容 |
|------|--------|--------|------|
| **任务分配** | 主 Agent | 子 Agent | 任务配置（系统提示词、工具权限、任务描述） |
| **任务结果** | 子 Agent | 主 Agent | 执行结果、修改的文件、状态 |
| **进度更新** | 子 Agent | 主 Agent | 当前进度、遇到的问题 |

### 5.5 上下文传递

主 Agent 给子 Agent 分配任务时，传递以下信息：

```
子 Agent 初始上下文 =
  + 系统提示词（角色定义 + 任务描述 + 要求）
  + 相关文件列表（预先确定好，减少子 Agent 探索成本）
  + 关键文件内容（可选，预加载重要文件）
  + 项目规则（MINI.md 中的相关规则）
  + 工具权限（按任务分配）
  + 工作目录限制（可选）
```

**为什么预先确定文件列表？**
- 减少子 Agent 的探索时间（不用自己找文件）
- 限制子 Agent 的操作范围（更安全）
- 提高效率（子 Agent 直接开始干活）

### 5.6 结果汇总

子 Agent 返回的结果格式：

```yaml
子任务结果:
  任务ID: T1
  name: auth-module-refactor
  状态: completed / failed
  修改的文件:
    - src/auth/mod.rs
    - src/auth/login.rs
    - src/auth/register.rs
  执行的命令:
    - cargo check: 通过
  遇到的问题: []
  详细说明: "将所有错误处理从 match 改为 anyhow::Result..."
```

## 六、调度策略

### 6.1 并行度控制

- **最大并行子 Agent 数**：5 个（固定上限）
- 子 Agent 数量由主 Agent 根据分析结果自主决定（最少1个，最多5个）
- 同一执行阶段内的子任务并行执行
- 不同阶段之间串行执行（有依赖关系）

### 6.2 失败处理

| 失败类型 | 处理策略 |
|---------|---------|
| 子 Agent 执行失败 | 同一轮内重试 1-2 次，仍失败则标记为失败，主 Agent 在汇总阶段处理 |
| 测试不通过 | 主 Agent 在汇总阶段决定是否修复（或创建新的子任务） |
| 文件冲突 | 主 Agent 在汇总阶段裁决，决定保留哪个版本或手动合并 |
| 超时 | 强制终止，标记为失败，主 Agent 决定是否重试 |

### 6.3 轮次机制

**默认单轮执行**：一次用户提问，主 Agent 分析 → 生成计划 → 子 Agent 分阶段执行 → 主 Agent 汇总修改 → 返回用户

**用户手动续轮**：
- 用户对结果不满意，可输入 `/team:continue "继续修改XXX"` 触发下一轮
- 主 Agent 基于上一轮结果继续执行
- 续轮可以是完整流程（重新分析）或精简流程（直接创建新的子任务）

**为什么默认单轮？**
- **成本控制**：避免自动多轮导致 Token 成本失控
- **用户掌握主动权**：用户决定是否继续投入
- **可预测性**：用户知道一次调用的成本上限

## 七、权限与安全

### 7.1 权限分级

按任务分配工具权限（最小权限原则），核心原则：

- **最小权限原则**：每个 Agent 只拥有完成任务所需的最少权限
- **只读优先**：审查类任务只给读权限
- **修改受控**：修改操作受审批管控
- **目录限制**：可选限制子 Agent 的工作目录

### 7.2 审批机制

多 Agent 模式下，危险操作需要审批：

| 操作 | 审批方式 |
|------|---------|
| 修改生产代码 | ⚠️ 用户审批（默认） |
| 修改测试代码 | ✅ 自动通过（主 Agent 事后审查） |
| 运行构建/测试命令 | ✅ 自动通过 |
| 运行危险命令 | ⚠️ 用户审批 |
| 修改配置文件 | ⚠️ 用户审批 |
| 网络请求 | ⚠️ 用户审批 |

### 7.3 文件锁机制

防止多个子 Agent 同时修改同一个文件：

```
子 Agent A 要修改 src/main.rs
  │
  ├─ 检查文件锁
  │    ├─ 未锁定 → 加锁 → 修改 → 解锁
  │    └─ 已锁定 → 告诉主 Agent，由主 Agent 调度
  │
  └─ 修改完成后释放锁
```

**锁的粒度**：文件级（每个文件一把锁）

**冲突处理**：
- 主 Agent 在任务计划阶段就应该避免让两个子 Agent 修改同一个文件
- 文件锁作为兜底保障
- 如果真的发生冲突，主 Agent 调整任务分配

### 7.4 沙箱隔离（可选的高级功能）

未来可以考虑：
- 每个子 Agent 在独立目录工作
- 修改完成后由主 Agent 合并到主目录
- 这样即使子 Agent 出问题，也不会影响主项目

## 八、错误处理

### 8.1 单个子 Agent 失败

```
子 Agent 失败
  │
  ├─ 失败次数 ≤ 2？
  │    └─ 是 → 重试（可能调整任务描述）
  │
  └─ 否 → 主 Agent 判断
       ├─ 非关键任务 → 标记失败，跳过，继续其他任务
       ├─ 关键任务 → 主 Agent 自己处理（或告诉用户）
       └─ 完全无法继续 → 终止团队会话，告诉用户失败原因
```

### 8.2 结果冲突

**定义**：两个子 Agent 对同一个文件有不同的修改意见

```
检测到冲突
  │
  ├─ 主 Agent 分析冲突内容
  │    ├─ 小冲突（不同位置修改） → 自动合并
  │    ├─ 中等冲突 → 主 Agent 裁决
  │    └─ 大冲突（完全相反的修改） → 问用户
  │
  └─ 裁决后 → 主 Agent 统一修改
```

### 8.3 超时机制

- 每个子任务有超时时间（默认 10 分钟）
- 超时后强制终止，标记为失败
- 主 Agent 决定是否重试

### 8.4 回滚机制

团队会话开始前，记录当前状态：
- git 分支（如果有 git）
- 或备份要修改的文件

如果团队会话失败，可以一键回滚到开始前的状态。

## 十二、成本与收益分析

### 12.1 Token 成本

**单 Agent vs 多 Agent Token 对比**：

| 场景 | 单 Agent | 多 Agent（4个子 Agent） | 倍数 |
|------|---------|----------------------|------|
| 简单任务 | 10k tokens | 30k tokens | ~3x |
| 中等任务 | 50k tokens | 100k tokens | ~2x |
| 复杂任务 | 200k tokens | 300k tokens | ~1.5x |

**为什么复杂任务倍数更低？**
- 复杂任务单 Agent 需要反复探索
- 多 Agent 分工明确，减少了重复探索
- 并行执行节省时间，Token 增加幅度小于时间减少幅度

**成本控制措施**：
- 用户主动触发（用户自己判断值不值得）
- 最大子 Agent 数限制（5个）
- 子 Agent 上下文预加载（减少探索）
- 默认单轮执行（不会自动多轮烧钱）

### 12.2 时间收益

| 场景 | 单 Agent | 多 Agent | 节省时间 |
|------|---------|---------|---------|
| 简单任务 | 5分钟 | 4分钟 | 20% |
| 中等任务 | 20分钟 | 10分钟 | 50% |
| 复杂任务 | 60分钟 | 25分钟 | 58% |

### 12.3 质量收益

- 独立审查环节 → 错误率降低
- 专业分工 → 代码质量更高
- 测试专门负责 → 测试覆盖率提升

## 十三、风险与挑战

| 风险 | 严重程度 | 应对策略 |
|------|---------|---------|
| Token 成本过高 | 高 | 用户主动触发、并行数限制、预加载减少探索、默认单轮 |
| 子 Agent 之间冲突 | 中 | 任务计划阶段避免、文件锁兜底、主 Agent 裁决 |
| 主 Agent 调度不合理 | 中 | 任务计划让用户确认、可调整 |
| 结果汇总质量差 | 中 | 审查模板把关、用户手动续轮 |
| 实现复杂度高 | 高 | 渐进式实现，先 MVP 再扩展 |
| TUI 展示复杂 | 低 | 先做简单展示，逐步优化 |
| 子 Agent 上下文不足 | 中 | 预加载关键文件、明确任务描述 |

## 十四、总结

多 Agent 团队模式是 MiniCode 的重要扩展，核心价值：

1. **提升效率**：并行执行，大任务更快完成
2. **提升质量**：专业分工 + 独立审查
3. **架构亮点**：区别于原项目的核心个人贡献
4. **面试话题**：可以深入聊调度策略、通信机制、冲突解决、成本控制等

**核心设计思想**：
- **任务驱动**：子 Agent 是动态创建的执行单元，不是固定角色
- **中心化调度**：主 Agent 统一管理，简单可控
- **上下文隔离**：每个子 Agent 独立上下文，避免污染
- **最小权限**：按任务分配工具权限，安全可控
- **单轮默认**：用户掌握主动权，成本可控

设计原则：**用户主动触发、中心化调度、任务驱动、上下文隔离、最小权限、渐进式实现。**
